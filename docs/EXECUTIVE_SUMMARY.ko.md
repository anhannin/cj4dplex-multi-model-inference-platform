# Executive Summary
## 하나의 GPU에서 두 AI 서비스의 간섭을 줄이는 운영 정책
**CJ 4DPLEX AI Platform 개발 사전과제 | 안하민 | 2026-11-12**

### 문제와 목표
한 대의 DGX Spark에서 문장을 생성하는 Qwen3.5-9B와 이미지를 검출하는 YOLO26l을 함께 운영했다. 모델 정확도 향상이 아니라, 서로 다른 AI 작업이 같은 GPU를 쓸 때 생기는 지연을 측정하고 안정적으로 요청을 처리하는 것이 목표다.

주요 시나리오는 **Qwen10건·YOLO300건이 한꺼번에 제출되는 제작 작업 묶음**이다. 실제 회사 트래픽을 수집한 것은 아니다. Qwen 전체 응답시간을 악화시키지 않으면서 YOLO의 늦은 응답(p95)을20% 이상 줄이는 상대 목표를 합의했다. Burst 결과를 탐색한 뒤 목표를 정했다는 점을 밝히며 사전등록된 독립 검증처럼 설명하지 않는다.

### 접근 방법
- 두 모델을 별도 컨테이너·Kubernetes Pod로 배포하고, 모델별 독립 대기열과 Worker를 사용했다.
- 요청별 전체 지연, 대기시간, 모델 호출, GPU forward 구간과 자원·로그를 수집했다.
- 최적화 없음·일반 MPS·고정 SM 분할5개 조합을 같은 환경에서 각각5회 비교했다.
- 생성의 Prefill은 많은 SM에서 빨라졌지만 반복 Decode는 SM 수에 비례해 빨라지지 않았다. 이를 근거로 **Qwen8 / YOLO40 SM** 분배를 검증했다. 단순히 GPU 공유 기능을 켠 것만으로 개선됐다고 주장하지 않는다.

### 주요 결과 — 최적화 없음 대비
| Burst 지표 | 최적화 없음 | 고정8/40 | 변화 |
|---|---:|---:|---:|
| YOLO300건 전체 완료 평균 |16.322초|11.592초|**28.98% 단축**|
| YOLO 요청 E2E p95 |14.963초|10.674초|**28.66% 감소**|
| Qwen 요청 E2E p95 |113.299초|111.876초|약1.26% 감소|

p95는 요청95%가 해당 시간 이내에 완료됐음을 나타내는 기술통계다. Burst p95는 조건별 요청을 합친 분포이며 실행 반복 단위는5회다. 전체 요청묶음 완료시간은 약1.30%만 줄었으므로 대폭적인 전체 처리량 개선으로 과장하지 않는다.

### 지속 요청에서 효과와 한계 확인
초당8개·15개의 YOLO 요청과 지속 Qwen 요청으로 총40회를 추가 측정했다. 지표는 **실행별 요청p95의5회 평균**으로, Burst 통계와 합치지 않는다.
- **15req/s:** 8/40에서 Qwen p95 **9.66%**, YOLO p95 **39.61%** 감소. 두 상대 목표 관측 충족.
- **8req/s:** Qwen **5.63%**, YOLO **16.25%** 감소. 개선됐지만 YOLO20% 목표 미달.
- 16/32도15req/s에서 두 목표를 충족했다. 8/40이 모든 업무·지표의 유일한 최적해는 아니다.

### 비용과 운영 리스크
SM을 적게 받은 Qwen의 내부 첫 토큰 생성시간은 지속15req/s에서 약**209→487ms**로 악화됐다. 최종 응답을 빨리 마치는 업무와 첫 반응이 중요한 대화형 업무는 우선순위가 다르다. 같은 조건의 YOLO GPU forward Event도11.31→16.84ms로 증가했으므로 전체 지연 개선을 GPU 연산시간만의 단축으로 설명할 수 없다.

GPU 공유는 메모리·대역폭·장애의 완전한 격리를 제공하지 않는다. UUID 응답 채널은 요청 혼선 방지이며 보안 인증이 아니다. 신뢰된 단일 호스트의 실험이며 외부 공개 서비스의 SLA나 장기 가용성을 보증하지 않는다.

### 장애 대응과 검증 범위
GPU 유휴·빈 큐를 확인한 YOLO Node를 강제 종료하고 **Kubernetes 기본 재시작**을 검증했다.3회에서 종료 신호 직전부터 첫 정상 결과 수신까지 **4.163~4.504초**였다. 직접 만든 복구 최적화나 무중단 서비스 성과가 아니다. 진행 중 요청 보존, GPU 실행 중 장애, 반복 CrashLoop는 검증하지 않았다.

### 결론과 활용
하나의 GPU에서 모델별 자원 민감도를 측정하고 실행 정책을 바꾸면, 언어 모델의 전체 응답시간을 유지하면서 CV 대기와 완료시간을 줄일 수 있었다. 동시에 첫 토큰 비용과 저부하 목표 미달을 공개해 정책의 적용 범위를 구분했다.

기존 운영 배포는 원래 설정으로 복구했다.8/40은 검토 가능한 후보이며 사용자 승인 없이 상시 운영 설정을 바꾸지 않았다. 다음 단계는 실제 업무 입력과 우선순위에 맞춘 독립 검증, 필요한 health·요청 보존 수준 결정이다.
