## 1. 프로젝트 개요

본 프로젝트는 공개된 사전학습 AI 모델과 기존 소프트웨어 프레임워크를 활용하여, 단일 GPU에서 서로 다른 AI 모델을 동시에 실행하는 추론 플랫폼을 구축하고 성능을 최적화한 과제이다.

AI 모델 자체를 개발하거나 재학습하는 대신, **모델별 독립적인 추론 서비스 구현, Kubernetes 기반 배포, ROS 2 통신 구조 설계, GPU 자원 경합 분석 및 최적화**에 중점을 두었다.

지원자는 핵심 추론 서비스와 배포·통신 시스템을 직접 구현하였으며, 일부 기능과 실험 자동화 코드는 AI 개발 보조 도구인 Codex를 활용하였다.

본 문서는 사용한 모델·소프트웨어·외부 서비스의 출처와 지원자의 직접 구현 범위, AI 도구의 활용 범위를 구분하여 설명한다.

## 2. 사용 AI 모델

| 모델 | 제공자 | 사용 목적 | 적용 방식 |
|---|---|---|---|
| Qwen3.5-9B | Qwen | 텍스트 생성 | 사전학습 모델, BF16 |
| YOLO26l | Ultralytics | 객체 검출 | 사전학습 모델, PyTorch FP16 |

### 2.1 Qwen3.5-9B

Qwen에서 공개한 사전학습 모델을 사용하였다. Qwen3.5-9B는 멀티모달 기능을 지원하지만, 본 과제에서는 텍스트 입력과 텍스트 생성 기능만 활용하였다.

Hugging Face Transformers와 PyTorch를 이용하여 모델을 로딩하고, `model.generate()`를 호출하는 추론 서비스를 구현하였다.

최신 성능 비교에서는 입력 512토큰, 출력 128토큰 조건을 고정하여 모델의 처리시간과 단계별 지연을 측정하였다.

모델의 네트워크 구조, 가중치 및 학습 알고리즘은 변경하지 않았다.

### 2.2 YOLO26l

Ultralytics에서 제공하는 YOLO26l 객체 검출 모델을 사용하였다.

PyTorch 기반의 원본 추론 경로를 활용하였으며, 입력 이미지 크기 640×640, 배치 크기 1, FP16 조건에서 성능을 측정하였다.

본 과제의 최종 GPU 자원 분할 비교에서는 모델 재학습이나 네트워크 구조 변경 없이 동일한 모델과 입력 조건을 유지하였다.

### 2.3 모델 활용 범위

두 모델 모두 공개된 사전학습 가중치와 기존 추론 기능을 활용하였다.

**본 과제의 성능 개선은 모델의 정확도나 구조를 변경한 결과가 아니라, 모델 실행 환경과 GPU 자원 배분 방식을 최적화하여 얻은 결과**이다.

따라서 모델 자체의 개발과 본 과제의 추론 플랫폼 구현을 명확하게 구분한다.

## 4. 지원자 직접 구현 범위

### 4.1 컨테이너 기반 AI 추론 서비스

Qwen과 YOLO를 독립적으로 실행할 수 있도록 컨테이너 내부의 추론 서비스 코드를 직접 구현하였다.

주요 구현 내용은 다음과 같다.

- Qwen 및 YOLO 모델 로딩
- 입력 데이터 수신 및 모델 입력 변환
- PyTorch 기반 추론 API 호출
- 추론 결과 처리 및 반환
- 모델 상주 실행을 위한 서비스 구성
- 모델별 독립적인 추론 실행 환경 구성

AI 모델의 내부 연산은 기존 PyTorch 및 모델 프레임워크가 제공하는 기능을 활용하였다.

지원자가 직접 구현한 부분은 이러한 기능을 실제 서비스에서 사용할 수 있도록 연결하는 추론 처리 로직과 실행 구조이다.

### 4.2 Kubernetes 배포 환경

두 AI 모델을 별도 Pod로 실행하고 관리할 수 있도록 Kubernetes 배포 코드를 직접 구현하였다.

주요 구현 내용은 다음과 같다.

- 모델별 Docker 이미지 구성
- Qwen 및 YOLO Deployment 설정
- 모델별 Pod 실행 환경 및 자원 설정
- 컨테이너 환경변수와 실행 경로 구성
- ROS 2 통신을 위한 컨테이너 실행 환경 구성
- 모델별 서비스 배포 및 실행 검증

Kubernetes의 Pod 관리 및 컨테이너 재시작 기능 자체는 기존 프레임워크가 제공하는 기능이다.

지원자는 이를 활용하여 두 AI 모델을 독립적으로 운영할 수 있는 배포 환경을 구성하였다.

### 4.3 ROS 2 기반 요청·응답 시스템

사용자의 요청을 모델별 추론 서비스에 전달하고 결과를 반환하는 ROS 2 시스템 구조를 직접 설계·구현하였다.

주요 구성은 다음과 같다.

- 모델별 독립적인 Request Topic
- ROS 2 Subscriber 기반 요청 수신
- 모델별 FIFO Queue 및 Worker 처리 구조
- 추론 완료 후 결과 Topic을 통한 응답
- 다중 요청을 지원하는 요청·결과 처리 구조

두 모델은 각각 독립적인 FIFO Queue와 Worker를 사용하며, 별도의 전역 실행 순서 조정 없이 하나의 GPU를 공유하도록 구성하였다.

#### UUID 기반 요청·응답 매칭

다수의 요청이 전달되는 환경에서 각 요청과 결과를 정확하게 대응시키기 위해 **UUID 기반 요청·응답 매칭 구조를 지원자가 제안**하였다.

해당 기능의 코드 구현에는 Codex를 활용하였으며, 실제 요청·응답 과정에서 UUID를 이용해 결과를 구분하도록 시스템에 통합하였다.

UUID는 개별 요청과 응답을 식별하기 위한 수단이며, 사용자 인증이나 접근 제어를 위한 기능은 아니다.

## 5. GPU 자원 최적화 및 검증 범위

### 5.1 최적화 전략 설계

단일 GPU에서 두 모델을 동시에 실행할 때 발생하는 지연 증가를 확인하고, 모델별 연산 특성에 따른 비대칭 SM 자원 배분 전략을 수립하였다.

성능 분석 결과, Qwen의 Prefill과 YOLO의 forward는 SM 수에 따른 처리시간 변화가 컸으나, Qwen의 반복적인 Decode 단계는 상대적으로 변화 폭이 작았다.

이를 바탕으로 Qwen에 상대적으로 적은 SM을 배정하고, 남은 SM을 YOLO에 집중하는 최적화 방향을 제안하였다.

**모델 특성 분석, 비대칭 자원 배분 아이디어 및 최적화 방향에 대한 기술적 의사결정은 지원자가 주도하였다.**

### 5.2 CUDA MPS 적용

CUDA MPS 정적 SM 분할을 이용하여 두 모델에 서로 다른 GPU 실행 자원을 할당하였다.

MPS 파티션 생성 및 설정 자동화 코드의 구현에는 Codex를 활용하였다.

지원자는 생성된 설정을 검토하고 실제 환경에서 다음 사항을 검증하였다.

- 모델별 SM 할당량
- MPS 정적 파티션 생성 및 적용
- 각 모델 프로세스와 파티션 연결
- GPU Kernel의 동시 실행 여부
- 자원 배분에 따른 모델별 성능 변화

MPS의 내부 구현이나 CUDA Kernel 자체를 수정한 것은 아니다.

본 과제의 기여는 **기존 CUDA MPS 기능을 활용하여 모델의 실행 특성에 적합한 GPU 자원 배분 전략을 수립하고, 이를 실제 추론 플랫폼에 적용해 검증한 것**이다.

### 5.3 최적 자원 배분 선정

동일한 모델과 입력 조건에서 MPS 미적용, 일반 MPS 및 5가지 정적 SM 분할 구성을 비교하였다.

실험 결과를 분석하여 Qwen 8SM / YOLO 40SM 구성을 선정하였다.

해당 구성에서 YOLO 300건의 완료시간은 MPS 미적용 대비 28.98%, 일반 MPS 대비 54.31% 감소하였다.

반면 Qwen 내부 첫 토큰 생성시간은 증가하였다. 이러한 Trade-off를 함께 분석하고, 전체 작업 완료시간과 YOLO 지연 개선을 기준으로 자원 배분 결과를 평가하였다.

## 6. Codex 활용 구현 범위

반복적인 코드 작성과 자동화 작업의 효율성을 높이기 위해 Codex를 개발 보조 도구로 활용하였다.

### 6.1 기능 구현 보조

지원자가 기능의 필요성과 동작 방식을 정의한 뒤, 구체적인 구현 코드를 작성하는 데 Codex를 활용하였다.

대표적인 사례는 다음과 같다.

| 기능 | 지원자 역할 | Codex 역할 |
|---|---|---|
| UUID 요청·응답 매칭 | 요구사항 및 시스템 구조 제안, 통합 검증 | 기능 코드 구현 |
| MPS 정적 SM 분할 | 최적화 전략 수립, SM 배분 방향 결정, 적용 검증 | 파티션 설정 및 자동화 코드 구현 |

### 6.2 부하 실험 자동화

반복적인 성능 측정을 위한 부하 생성 및 계측 자동화 코드는 Codex를 활용하여 작성하였다.

주요 기능은 다음과 같다.

- Qwen 및 YOLO 요청 자동 발행
- 동시 요청 부하 생성
- 반복 실험 수행
- 요청별 지연 및 처리시간 수집
- 실험 결과 저장과 집계
- 성능 비교 및 시각화 보조

지원자는 실험 목적과 비교 조건을 검토하고, 실제 장비에서 실험을 수행하여 결과를 분석하였다.

특히 모델별 성능 차이와 자원 경합을 해석하고, 후속 최적화 방향을 결정하는 과정에 중점을 두었다.

### 6.3 장애 주입 및 복구 실험 자동화

장애 상황을 재현하고 복구 시간을 측정하기 위한 자동화 코드 역시 Codex를 활용하여 작성하였다.

주요 기능은 다음과 같다.

- 대상 프로세스 확인
- 제어된 프로세스 강제 종료
- Kubernetes 컨테이너 재시작 관측
- 정상 응답 재개 확인
- 장애·복구 시점 기록

지원자는 장애 시나리오와 검증 범위를 검토하고, 실제 장비에서 장애 주입 실험을 수행하여 복구 동작과 측정 결과를 확인하였다.

해당 실험은 Kubernetes가 제공하는 기본 재시작 기능을 검증한 것으로, 별도의 자체 Failover 시스템을 구현한 것은 아니다.

## 7. 외부 API 및 서비스 사용

본 과제에서 Qwen과 YOLO의 추론은 단일 DGX Spark 내부의 GPU에서 직접 수행하였다.

외부 클라우드 AI 추론 API를 호출하여 모델 실행을 위임하지 않았으며, 측정 결과는 로컬 환경에서 실행한 모델의 처리시간을 기준으로 수집하였다.

따라서 ChatGPT나 다른 외부 생성형 AI 서비스의 응답시간을 본 프로젝트의 추론 성능으로 사용하지 않았다.

사전학습 모델 가중치와 필요한 패키지를 확보하기 위해 각 제공자의 공식 배포 경로를 활용하였으며, 해당 다운로드 경로는 실제 추론 처리 경로와 구분된다.

모델과 프레임워크의 기존 구현을 지원자가 개발한 것으로 표시하지 않으며, 공개 저장소에 포함하는 소스 코드·모델 가중치·외부 자료는 각각의 라이선스와 출처를 확인하여 관리한다.

## 11. 결론

본 과제는 공개된 AI 모델과 기존 소프트웨어 기술을 활용하되, **이를 단일 GPU에서 안정적으로 운영하기 위한 추론 플랫폼을 구축하고 자원 경합을 분석하여 최적화하는 과정**에 중점을 두었다.

지원자는 컨테이너 기반 추론 서비스, Kubernetes 배포 환경 및 ROS 2 통신 시스템의 핵심 구조를 직접 구현하였다. 또한 모델별 연산 특성 분석을 기반으로 비대칭 SM 자원 배분 전략을 제안하고, 실제 성능 측정을 통해 최적화 효과와 Trade-off를 검증하였다.

Codex는 UUID 매칭과 MPS 설정 등 일부 기능 구현, 부하 및 장애 실험 자동화, 문서화 과정에서 개발 보조 도구로 활용하였다.

**본 프로젝트의 핵심 기여는 기존 기술을 단순히 결합하는 데 그치지 않고, AI 모델의 실행 특성과 시스템 병목을 분석하여 적절한 자원 배분 전략을 설계하고 실제 운영 지표로 검증한 데 있다.**
