# 기본 성능 측정 결과 — 2026-11-03

## 결론

요청한 5조건 측정과 네이티브 UUID/이미지 기능 테스트를 완료했다.
본 측정 요청 **12,324건 모두 성공**, DDS ACK 실패0, 측정 Pod 재시작0.
두 Deployment는 현재 replicas1 / Ready1이다.

단순히 두 모델을 메모리에 상주시킨 경우 모델 실행시간은 거의 같았다.
둘 다 활성화한 조건에서는 같은 Pod의 개별 활성 조건 대비:
- Qwen 평균 E2E **+37.62%**, 전체 생성시간 **+37.90%**, 요청 처리량 **-27.34%**.
- YOLO 평균 E2E **+71.24%**, inference 구간 **+117.73%**, 처리량 **-41.06%**.
이는 이 단일 ordered closed-loop 실행에서 관측한 값이다. SM/메모리 대역폭/CPU
중 어느 자원이 원인인지는 이 결과만으로 확정하지 않는다. 최적화는 적용하지 않았다.

## Qwen

시간 단위는 표의 단위를 따른다. TTFT는 generate 진입→서버 첫 토큰 관측이다.

| 조건 | E2E 평균(s) | E2E p95(s) | generate 평균(s) | TTFT 평균(ms) | TPOT 평균(ms/token) | 처리량(req/s) |
|---|---:|---:|---:|---:|---:|---:|
| ① 단독 Pod | 11.561 | 11.606 | 11.551 | 97.95 | 90.18 | 0.08649 |
| ③ 둘 상주·Qwen만 | 11.575 | 11.635 | 11.548 | 98.22 | 90.15 | 0.08639 |
| ⑤ 동시 활성 | 15.930 | 16.219 | 15.925 | 131.48 | 124.35 | 0.06277 |

전체 generate는 Prefill/Decode와 CPU 생성 제어 등을 포함하며 순수 GPU 커널 시간이 아니다.
TTFT도 Prefill과 같지 않다. 현재 ROS는 최종 응답만 반환하므로 client TTFT가 아니다.
정확한 Prefill/Decode GPU forward 계측은 이번에 추가하지 않았다.
EOS 포함 관측 규칙을 정의했으나 이번 측정은 모두128토큰 상한 종료였다.

후처리를 무조건 NMS라 부르지 않는다. 실제 서비스 처리량을 측정했으며
1000/inference_ms를 FPS로 대체하지 않았다.

## 큐와 추론 외 지연

평균 큐 대기: Qwen①0.681 / ③0.644 / ⑤0.732ms,
YOLO②0.189 / ④0.188 / ⑤0.341ms.
이번 C1 부하에서는 큰 애플리케이션 큐 대기를 재현하지 않았다.

YOLO④는 inference 평균이②와 비슷한데 E2E p95는95.6ms였다.
④에서 추론 외 transport/client 잔여구간 p95가83.3ms로 관측되었다.
이 잔여구간에는 DDS 전송·executor·클라이언트 처리 등이 섞이며, 순수 네트워크
지연이 아니다. ACK 대기 구간과 겹치지만 ACK 자체가 원인이라고 확정할 수 없다.
따라서 p95는⑤에서④보다 오히려 작다. 평균/inference 악화와 tail 변동을 구분해야 한다.
반복·순서 교차·고정 도착률 측정 없이는 안정적 p95나 원인을 단정하지 않는다.

## 계측 오버헤드

워밍업 후 동일 입력64토큰 상한으로 basic/tokens 6쌍을 교차 비교했다.
모든 쌍의 출력 문자열 동일, 출력 토큰 관측 수 일치.
generate 시간 비율 차이의 중앙값은 **-0.0128%**로 측정 변동 수준이었다.
미리 정한 5% 기준에 따라 모든 본 조건에서 tokens 모드를 사용했다.
공통 타이머/로그 자체의 OFF 대비 비용은 측정하지 않았고,128토큰에서 별도의
오버헤드 재검증을 한 것은 아니다. 토큰별 출력·파일쓰기·GPU synchronize는 없다.

## 출력 재현성 주의

입력 해시, 입력 토큰 수, 출력128토큰은 모든 Qwen 조건에서 일치했다.
다만 Pod를 재시작한①→③에서30건 중18건의 문자열이 달랐다.
각 조건 내부에서는 같은 프롬프트의 반복6회 출력이 같았고, 같은 Pod에서 수행한
③↔⑤의30건 출력은 모두 일치했다. 예: hold/schedule 같은 일부 표현 차이.
비트 수준의 재시작 재현성을 확보한 것은 아니며 원인은 아직 분석하지 않았다.
greedy 설정만으로 재시작 간 문자열 일치를 검증했다고 주장하지 않는다.
최초 report의 문자열 완전 일치 검사는 이 차이를 탐지하여 실패했고, 데이터는
보존한 채 입력/토큰 작업량 일치 검증과 문자열 차이 보고를 분리했다.

## 로그 회전 복구와 검증

⑤ YOLO 로그가 CRI 10MiB 경계를 넘어 회전되어 kubectl logs만으로는7,234건의
전송 후 상세 이벤트가 빠졌다. 회전 파일과 현재 파일을 읽기 전용으로 회수하여
재결합했고, 현재는 모든 요청의 publication/processing 이벤트가 연결되었다.
두 원본 파일 크기:10,665,584 / 5,994,286bytes. 회수 총36,758행.
잘린 최초 kubectl 로그도 별도 보존했다. GPU/서비스 설정은 변경하지 않았다.

최종 검증:
- 서버 이벤트 누락0, 음수 잔여시간0, ACK 실패0.
- 각 조건 실제 Pod 수1/1/2/2/2, Ready 및 재시작0.
- 컨테이너 실행 소스 SHA256과 로컬 소스 일치.
- 두 모델의 물리 GB10 UUID 동일.
- 추가 네이티브 클라이언트4건 성공, UUID 혼선0, 이미지2장 저장, 원본 무변경.
- 로컬 단위/구조 테스트65개 및 Ruff 통과.

다음 장기 실행 전에는 stdout 회전 크기를 고려한 지속 로그 수집이 필요하다.
이번 회전 로그는 모두 보존되어 복구했지만, 더 긴 실행의 로그 보존은 보장하지 않는다.
